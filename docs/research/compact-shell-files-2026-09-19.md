# Компактный Shell и серверные файлы

Предложение по текущему коду, 19 сентября 2026. Это проектирование, не внедрение
нового workspace или серверного подключения в site/studio.ts.

## Раскладка

Одна строка глобальных действий: Файлы, имя проекта/подключение, поиск файла,
контекстные действия проекта, разворот. Инструменты схемы остаются в её панели.
Дерево проекта шириной 200–240 px сворачивается. Отдельная постоянная колонка
иконок не нужна. В дереве только реальные файлы; HMI, история и сигналы являются
представлениями, не фиктивными файлами. Папки строятся из относительных путей.

Код и визуальные представления открываются вкладками с возможностью разделить
рабочую область. Клик по файлу открывает preview-вкладку; повторное осознанное
закрепление или редактирование сохраняет вкладку. Несохранённая вкладка никогда
не заменяется другим preview. История и позиция курсора принадлежат документу.
Навигация между файлами не пересоздаёт проектный runtime.

Свойства — правая панель по выбору объекта; на узкой ширине overlay или отдельный
экран. Панель дерева на лендинге закрыта. При первом открытии файлов из серверного
проекта можно раскрыть дерево, но не открывать автоматически код и свойства.
Пользовательская раскладка затем восстанавливается. Нижняя панель диагностики,
журнала и изменений открывается по запросу. Ошибка обозначается счётчиком и
маркером у файла. Высота постоянной status bar — около 24 px.

На ширине менее 1000 px не сжимать четыре колонки; дерево временно накладывается
поверх рабочей области. На телефоне файл/схема/свойства занимают одну область.
Поиск файла и переход от объекта к исходному диапазону помогают обходиться без
постоянно раскрытого дерева. Полное docking-поведение можно добавить позже.

## Уже существующая серверная граница

plant/server.ts: GET /plant/api/project вызывает Service.files(actor).
Ответ — Revision: id, parent, time, actor, message, files: Record<string,string>.
Доступ к исходникам в текущем plant требует engineer, это не право всех viewers.
GET /plant/api/session возвращает head, desired и frame.revision: это разные
состояния (последний commit, желаемая публикация, реально выполняемая версия).
Не обозначать HEAD как выполняемую версию без проверки applied frame.

В старой однофайловой IDE также существует /api/projects/:id, с другим контрактом
и правилами. Не смешивать эти API: текущему новому workspace нужен адаптер plant.

Для нынешних размеров проекта достаточно одной загрузки карты файлов в рамках
одной ревизии: дерево выводится из ключей. Не строить отдельный файловый backend
и не запрашивать сервер при каждом раскрытии папки. Список путей не задаётся в UI
вручную и не извлекается из модели оборудования. Для больших проектов отдельный
manifest/content API может появиться позже с привязкой обоих ответов к ревизии.

## Владение состоянием

1. Repository snapshot: авторитетные файлы базовой серверной ревизии.
2. Document store: локальные изменения поверх snapshot, версии, undo и diagnostics.
3. Compiler projection: весь snapshot + все открытые и закрытые dirty документы.
4. Runtime session: отдельно живущая подписка на активную опубликованную версию.
5. Shell layout: вкладки, размеры, выбранный файл, дерево; хранится отдельно.

Схема, HMI и свойства запрашивают точечные изменения через Document store;
CodeMirror не является владельцем всего проекта. Проверка базовой версии текста
защищает визуальные правки от устаревших source ranges. Новые серверные данные
не перезаписывают локальные изменения. Состояние грязного документа сохраняется
при переключении и закрытии представления.

Commit использует существующий expected/base revision: конфликт требует
сравнения, а не последней молчаливой записи. Publish — отдельное действие после
commit; локальное сохранение не публикует проект. При обновлении сервера без
локальных изменений snapshot можно заменить; при локальных изменениях сохранить
их и показать возможность сравнить и применить новую ревизию.

Сессионные данные и серверные исходники не добавляются в публичный PWA precache.
Сохранение серверных черновиков для офлайн-работы требует отдельной политики
пользователя/проекта; установка публичного PWA сама по себе этого не разрешает.
Разрыв соединения не переключает установленный серверный проект в симуляцию.

## Порядок реализации

Сначала Document store и адаптер существующего project API; затем дерево и
вкладки на настоящих серверных файлах; далее компиляция многофайлового plant и
общие source edits. Текущий site монтирует однофайловый compiler @saturn/core:
добавить к нему дерево недостаточно для поддержки plant.ts с imports.

Первый проверяемый сценарий: загрузить ревизию с вложенной папкой → открыть два
файла → изменить первый → вернуться и отменить изменение → выбрать объект и
перейти к объявлению → получить серверное обновление, сохранив черновик.
Отдельно проверить HEAD/desired/applied, denied access, потерю связи, конфликт
commit и сохранение одной runtime-сессии при переключении панелей.

## Реализованный первый проход

Компактное дерево, фильтр, preview/закреплённые вкладки, отдельные EditorState,
переключение без потери undo, source navigation и правки числовых литералов
работают в site. Добавлен ленивый адаптер многофайлового plant compiler и
существующего project API. Импорт/экспорт карты файлов и локальные копии
сохраняются; серверные черновики автоматически не записываются на диск браузера.
Ожидающая серверная ревизия не заменяет изменённые документы.

Это пока authoring workspace. Подписка на runtime, серверные commit/publish,
полноценное сравнение/слияние версий, произвольное docking и общий visual editing
всех видов DSL остаются отдельными шагами. В текущем интерфейсе эти возможности
не выдаются за подключённые. На серверных исходниках запускается только
компиляция/проекция; нет автоматического выполнения модели вместо сервера.
